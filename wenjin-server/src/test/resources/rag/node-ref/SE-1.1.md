## 概念
软件需求描述系统必须具备的能力、约束与质量属性，是后续设计、实现与验收的依据。需求通常分为功能需求与非功能需求：前者回答系统做什么，后者回答做得多好（性能、安全、可用性、可维护性等）。干系人识别、需求获取、分析建模、规格说明与验证构成需求工程主链路。清晰的需求应可验证、可追溯，并尽量无歧义。

## 关键要点
获取阶段综合访谈、观察、原型与文档分析；分析阶段区分业务需求、用户需求与系统需求层次。规格说明可用自然语言加用例/用户故事，关键约束单独列出。变更要走影响分析：改一条需求可能波及测试与接口。对学生而言，先会写“可测的验收条件”，比堆砌形容词更重要。

## 常见误区
把愿望当需求（“系统要好用”却无可测指标）、把方案当需求（直接规定具体算法或界面布局却未说明问题）、以及需求漂移却不更新基线。纠正：为每条需求补验收标准，分离问题空间与解空间，并建立变更记录。
